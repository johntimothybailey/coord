# Verification runner and qualification boundary

`runVerification({ runtime, repo, head, tree, base, environmentDigest })` returns one `VerificationEvidence` containing the exact final head/tree, relevant target base, environment digest, approved command argument arrays, actual exit codes and observation time. It accepts `RuntimeConfig` from the protected command runtime. It does not accept a command callback, executable plugin, caller-created evidence object or unsandboxed fallback.

Only `runtime.policy.verificationCommands` can execute. The runtime is snapshotted before use. Command executables must resolve inside explicit canonical system/toolchain roots, and the sandbox executable must be the fixed preinstalled OS tool. Nothing is installed. The first implementation carries no copied application/provider environment: the sandbox receives only a fresh private HOME/TMP, a validated toolchain PATH, locale and timezone. `policy.verification.searchPath` may select a narrower verification-only PATH; when absent it defaults to `policy.searchPath`. An override is part of the runtime fingerprint and cannot add readable roots or admit worker/control tools. Any nonempty `copyEnvironment` or manual/managed application-environment requirement is rejected before subprocesses. The runner cannot certify a preflight environment whose values were silently omitted during tests. Verification that needs application/provider credentials or host network access remains unsupported.

## Current support

The implemented execution path is Linux `linux-bubblewrap`, explicitly selected at `/usr/bin/bwrap` or `/bin/bwrap`, with a protected root-owned regular executable. It creates private user, PID, network, IPC and UTS namespaces, drops all capabilities, prevents nested user namespaces, starts a new session and enforces `--die-with-parent`. The artifact and toolchain roots are mounted read-only; scratch is a private tmpfs. No host home, credential directory, control socket or repository Git directory is mounted. Namespace-local loopback may be available; it does not expose host loopback or host networking.

The `macos-sandbox-exec` selection is deliberately **BLOCKED**. Apple documents sandbox-exec as deprecated. Denying process forks could narrow descendants, but sandbox-exec alone does not stop a surviving child when its coordinator dies. A caller-supplied PASS record cannot make that missing containment mechanism exist. macOS execution requires a concrete parent-death containment implementation and independent qualification before this branch can be enabled. The actual local macOS sandbox probe on November 6, 2026 also returned `sandbox_apply: Operation not permitted`; no real verification command was run through it.

Linux is an implemented path, not a qualification result. No Linux host was available in this slice, and no real Linux sandbox or provider/harness isolation is claimed.

## Required protected evidence

Every call requires one current `verification.sandbox` capability check with `kind: real`, `status: PASS`, a non-advisory mode, evidence reference and observation within 24 hours. Its configuration digest and the capability key's configuration digest must equal the current protected runtime digest. Missing, duplicate, future, stale or fixture checks fail closed before commands. The main runtime must authenticate and compare owner-provisioned backend qualification records before calling this helper; a local caller-created PASS is not authority. This component check does not replace the rest of the manual/managed host qualification. Privileged metadata inspection additionally requires the existing current `git.metadata-write-isolation` proof and full manual/managed prerequisites before any Git subprocess.

The runner also performs its own fixed literal Node probe before any repository command. The probe uses generated synthetic control/read-only canaries, never real credential values. It checks hidden control data, read-only artifact behavior, writable scratch, the empty inherited environment, readable executable visibility, successful contained child execution and distinct PID/network namespace identities. A fixed harmless Node baseline must succeed first. A failed native setup/probe cannot be relabeled command success.

## Exact artifact and safe roots

Before execution, trusted fixed Git metadata commands verify `HEAD`, `HEAD^{tree}`, the exact relevant base object and an index identical to the requested tree. A different head, staged content or non-ignored untracked content blocks verification. These fixed Git calls use a cleared environment, no system/global Git configuration, disabled hooks/fsmonitor and disabled replacement objects. Lazy fetch is disabled and the transport allowlist is empty; credential helpers, SSH commands and automatic maintenance are disabled. Missing/promisor objects block verification rather than causing any network fallback. On macOS, metadata inspection uses the fixed Command Line Tools Git binary directly rather than invoking the Xcode-select shim with inherited environment.

The runner checks every tracked working-tree blob against its Git object identity and mode, using bounded reads, regular-file no-follow handles and symlink target identity. It materializes only that exact tracked tree into a fresh private artifact. Git metadata, ignored dependency caches and untracked local/control files are never copied. This first implementation consequently cannot reuse ignored `node_modules`; projects needing dependency preparation need a separately approved, isolated setup path rather than installing during verification.

Allowed roots are a narrow fixed set of system directories or recognized versioned Node/Homebrew toolchain directories. Broad `/`, `/usr`, `/System`, all HOME, workspace/worktrees, coordinator state, worker/GitHub homes (including the actual Git transport HOME), trusted startup-registry directory, agent credential sources, role credential directories and their overlapping ancestors/descendants are rejected. Toolchain roots must be canonical, non-overlapping directories without group/other write permission. Operator qualification must also establish effective worker restrictions and toolchain integrity; file modes alone do not prove isolation.

Before and after every command, the runner revalidates source head/tree/base/index and all source blob identities. It also checks the isolated artifact for changed blobs, modes and unexpected added files/directories. Passing tests on altered code cannot produce evidence for the original tree. The relevant live remote base still needs provider readback/revalidation in the surrounding publication protocol; local base-object existence is not remote verification.

## Bounds and failures

Each subprocess is limited to 30 seconds and 1 MiB combined stdout/stderr. Output is discarded and never included in evidence or error messages. The tree is bounded to 20,000 files, the selected per-file capture bound and 64 MiB total content. There are at most 50 approved commands. No command is interpolated into a shell.

A nonzero exit, mismatching source/artifact or limit violation yields no passing evidence. On a limit, the runner kills the fixed bubblewrap containment and requires a positive close event. A process-group kill is not used as proof of containment. If positive exit is not observed, the call reports `LAUNCH_UNCERTAIN` and retains its private scratch for operator inspection. The publication/task result and harness capacity lifecycle remain separate backend facts.

## Tests and references

`tests/verification-runner.test.ts` exercises configuration/qualification denial, exact source and evidence binding, fixed sandbox arguments and empty environment, failed probes/commands, source/artifact changes, unexpected artifact files, output/time bounds, positive exit and retained scratch on unknown exit. Its positive-path subprocess and Linux namespace interactions are explicitly mocked. The fixture never executes repository commands outside a real sandbox, and it cannot enable the blocked macOS branch. These tests are rehearsal evidence only.

Primary references consulted: the installed Apple `sandbox-exec(1)` and `sandbox(7)` manuals (including inherited restrictions and already-open descriptor caveats), Apple's installed sandbox profile definitions, the upstream [bubblewrap security model](https://github.com/containers/bubblewrap/blob/main/README.md), and its [native option definitions](https://github.com/containers/bubblewrap/blob/main/bwrap.xml). Bubblewrap's documentation makes the surrounding argument policy responsible for the boundary; having the executable installed is insufficient.
