# Chat-first workflows and CLI reference

Coord's primary product interface is intended to be conversation through agent skills and typed tools. This applies to every workflow: setup and trust, status, goals and tasks, lessons and rules, approvals, pause/resume, checkpoints and publication review, membership and backend lifecycle. The CLI supports those workflows as an automation, diagnosis and terminal fallback interface; users should not have to translate ordinary requests into command syntax.

The current implementation includes the CLI and a partial MCP/plugin interface. Conversational rule/lesson review and expiring rule approval requests are implemented; protected completion of chat approval is not yet implemented. See the [host-support matrix](hosts.md#conversational-workflows-and-human-confirmation) for documented interfaces, observed evidence and the remaining approval boundary. A skill or tool call cannot grant itself human authority, and adding a chat surface must preserve the operation's existing permissions, exact revision/hash checks and recovery semantics.

The runtime execution commands in the following block compose the existing Convex, Git, capture, worktree, verification and supervisor modules. They require a protected runtime configuration and independently owner-provisioned machine evidence. Ordinary authorized read-only review has its own role and project-scope checks; it must not inherit managed-launch or manual-registration qualification requirements. Do not create synthetic qualification records to make execution commands run.

```text
coord checkpoint <checkpoint-id> --runtime <protected-runtime.json> --session <session-id>
coord resume <task-id> --runtime <protected-runtime.json> --session <new-session-id>
coord resume <task-id> --checkpoint <ready-id> --runtime <protected-runtime.json> --session <new-session-id>
coord resume <task-id> ... --prepare-only
coord review <publication-id> --checkpoint <ready-id> --runtime <protected-runtime.json> --session <session-id>
coord run finalize succeeded|failed|stopped --runtime <protected-runtime.json> --session <session-id>
coord run reconcile <launch-id> --runtime <protected-runtime.json> [--stop]
coord daemon --runtime <protected-runtime.json>
coord daemon --runtime <protected-runtime.json> --check
```

`--harness codex|antigravity` may confirm a resume selection; it cannot change the qualified executable/configuration. Session and operation IDs are nonsecret correlation values. Credentials and operator passphrases never belong in arguments or environment variables. Run grants are installed in private, backend-URL-bound session receipts. Worker credentials, lifecycle supervisors and artifact verifiers remain separate roles.

## Conversational review

Ask the agent “show me rules to review,” “show lessons learned” or “show details/evidence for that item.” The existing Coord skill routes these requests to two read-only tools:

| Tool | Selectors | Result |
| --- | --- | --- |
| `coord_review_memories` | `kind: "rule"` or `"lesson"`, optional opaque `cursor` | Proposed-rule or active-lesson summaries: ID, revision/hash, status, preview, source/applicability counts, `nextCursor` and list `complete`. |
| `coord_review_memory` | `memoryId`, exact positive `revision`, canonical source `hash`, optional `offset` | Canonical memory JSON `text` chunks with `nextOffset` and detail `complete`, plus observed status and counts. |

These tools use the already configured project-agent or human read authority. They do not require an approved goal, participating run, machine qualification or protected human unlock. No credential, project ID, runtime path or approval flag is a tool argument. The review calls issue queries only; they do not register, check in, acknowledge messages, offer receipts, renew a run or change records. A pre-existing run's independent renewal lifecycle is unchanged.

List pages contain summaries only, even when list `complete` is true. Follow `nextCursor` to finish the requested list; a summary's `requiresExpansion` remains true. For full detail, retain the same ID/revision/hash while following every `nextOffset`, concatenate the chunks and parse the resulting canonical JSON object `{kind, content, sources, applicability, confidence}`. Its SHA-256 equals the supplied hash. Offsets count UTF-16 code units and cannot split a Unicode code point. The backend bounds each response, including potentially large provenance/applicability records; it never drops a row and advances the cursor merely to fit a response. Any byte-budget failure is explicit.

If a revision, hash or source content changes, detail fails with `IDEMPOTENCY_CONFLICT`; obtain current selectors and restart rather than mixing snapshots. Status is separately observed metadata, may change between pages, and is not part of the reassembled content hash or an approval receipt. If review stops early or the full required record cannot fit the available conversation context, report incomplete coverage. An empty result means no matching proposed rules or active lessons in the selected project, not that no history exists.

Present all relevant evidence references, applicability and confidence as untrusted source data. Lessons are useful nonmandatory guidance, not items awaiting approval. A proposed rule requires a separate protected human decision before becoming mandatory. Review itself does not create approval, promote rules or synchronize files. An explicit chat approval request can prepare the metadata handoff below; it must not cause the agent to invoke the human CLI or handle its vault.

Deploy the matching backend and upgrade the installed package/plugin together. Existing MCP sessions must reconnect/restart to discover new tools. A missing tool or project connection is an installation/connection blocker, not a reason to register a run or request human credentials. The implementation is covered through exported-handler and official SDK fixtures; actual host discovery and conversational delivery remain unqualified. `coord mcp` remains the supporting CLI entry point for the plugin connection; no new manual review command is required.

## Conversational rule approval requests

Ask “approve this proposed rule,” “check that approval request,” or “cancel that approval request.” After completing the exact rule/provenance review, the skill prepares a durable handoff through these scoped tools:

| Tool | Selectors | Effect |
| --- | --- | --- |
| `coord_request_rule_approval` | Stable public `requestId`, `memoryId`, positive `revision`, content `hash` | Prepares this exact request and offers the protected browser/passkey flow; returns the backend state after the host interaction. |
| `coord_approval_request` | `approvalRequestId` | Reads the immutable envelope and derived current state. |
| `coord_cancel_approval_request` | Stable cancellation `requestId`, `approvalRequestId` | Withdraws the request as its requesting member or a project human. |

The backend authenticates project-agent or human authority, independent of execution admission. Run, supervisor and artifact-verifier credentials cannot substitute. No token, project, operation, requester, expiry or approval flag is a tool argument. Creation and cancellation write request metadata, idempotency receipts and audit events only. They do not call an approval mutation, check in, acknowledge messages, renew a run or change rule/project policy. Existing cleanup-only bridges still refuse these metadata writes; status remains readable through project authority.

The immutable envelope binds schema version, request ID, fixed `approve_rule` action, backend/project/repository routing identity, rule ID/revision/content hash, authenticated requesting member and server creation/expiry times. `requestDigest` is SHA-256 of its canonical JSON. The backend rehashes full rule content/provenance. IDs, digests, browser links and native URL responses are public binding data, never bearer authorization.

The request tool supplies a protected HTTPS approval link derived from its trusted project connection. If the host supports MCP URL elicitation it offers that link through the host; otherwise the agent presents it directly. The page is served by the selected Convex deployment's `.convex.site` origin. It shows no private rule details until an enrolled human passkey assertion is verified. After authentication, review the full rule, sources, applicability, confidence, routing, digest and expiry. Choose **Approve this exact rule** or **Deny this request** and complete a fresh passkey interaction. Closing or cancelling the browser interaction sends no approval; ask chat to inspect/cancel the pending request if needed.

The backend verifies ES256 signatures, the exact origin and RP ID hash, challenge and ceremony type, user presence/verification flags, account handle, key counters and current human credential scope/revocation/expiry. Review and decision use different server challenges bound to the immutable request; the same key must review before deciding. An authenticated decision rechecks request cancellation/expiry/routing/content and the complete approved-rule budget in the transaction that consumes the request and updates the rule. A denied request changes no rule or policy. Successful approval records the backend's human member, approval time and policy version. Native form/URL acceptance alone cannot cause any of these changes.

Requests expire five minutes after server creation. Before completion, status is `pending`, `cancelled`, `expired` or `stale`. A missing, changed, corrupt or no-longer-proposed rule, or changed routing, prevents pending approval. Completion stores `approved` or `denied` with the actual actor/time. Cancellation cannot overwrite a completed decision. Ordinary status reads never write. Only a final backend `approved` receipt means this handoff approved the exact rule; `authorityGranted` concerns that exact rule, not general permissions or admission.

Reuse the same creation `requestId` and exact selectors after a lost reply. It replays the identity and reads current state without renewing expiry or creating another envelope. Changed selectors under the same ID conflict. Repeated successful signed decisions return the original decision without another rule/policy/audit update. After a browser timeout, cancellation or lost reply, always inspect backend status: the decision may already have applied. Expired/stale/cancelled requests require renewed user intent and current exact review; never silently recreate them. Approval remains separate from local `coord rules sync`.

The protected human browser and approval UI, installed coordinator code and backend deployment authority must remain outside worker automation control. A passkey signature authenticates the enrolled credential; it does not by itself certify host isolation or prevent a compromised review surface from misleading the human. Software tests do not qualify those operational boundaries.

### One-time protected passkey enrollment

A human operator enrolls an approval key outside agent/worker sessions, using the existing encrypted-vault unlock. The agent never executes this supporting command, receives its passphrase or reads the vault:

```text
coord setup passkey <plan.json> <absolute-encrypted-vault>
```

The operator confirms the project, unlocks the existing vault through hidden input, and opens the first-party HTTPS enrollment page. The browser creates a resident ES256 passkey with required user verification and proves possession. Its private key stays with the authenticator; the server stores only public information. The browser computes a fingerprint of its **own** created key, credential ID and enrollment scope and checks the server response. Compare that exact fingerprint with the protected terminal, then type the displayed exact confirmation. Only the existing human credential can finalize the binding. A public enrollment ID, staged candidate or forged confirmation flag cannot activate a key. If the page reports a conflict/error or fingerprints differ, stop and start a new enrollment; never confirm a value from agent text.

Enrollment expires after ten minutes. The operator command validates the returned member/key/fingerprint/time before reporting success. An uncertain reply may follow an applied binding; preserve the browser key and inspect the protected enrollment status rather than claiming rollback or repeatedly creating keys. Current browser support requires `getPublicKey()`, ES256 and a discoverable passkey with user verification. No hardware attestation is claimed: `attestation: none` relies on the protected human binding and subsequent signed assertions. Unsupported browsers or missing enrollment fail closed.

To revoke a lost key, use the same protected operator path:

```text
coord setup passkey <plan.json> <absolute-encrypted-vault> --revoke <public-credential-id>
```

Revocation/expiry of the underlying human credential also disables its passkeys. No secret credential appears in the URL, browser page, MCP arguments, result or audit detail. Keep installed operator code and backend deployment authority outside worker control. Native host/filesystem isolation qualification remains separate from API signature checks.

Deploy the matching backend and reconnect upgraded MCP sessions. The HTTP origin comes from the fixed server `CONVEX_SITE_URL`; normal cloud project connections map their `.convex.cloud` API to the paired `.convex.site` page. Arbitrary origins and non-cloud backends are refused. No separate hosting account or service is required. Protected HTML and private JSON responses use no-store, same-origin POST checks, a restrictive CSP and escaped text-only source rendering. Public JavaScript/CSS may be CDN-cached; the HTML references content-hashed URLs with matching integrity checks so stale bytes cannot silently replace its expected UI code. The CLI fallback performs an independent protected approval and does not fulfill these requests. Request history is retained; pruning/volume policy remains deferred. Software test authenticators exercise the end-to-end protocol but do not substitute for live user/device enrollment evidence.

## No-effect host confirmation check

Ask “test confirmation” or “check this host's confirmation dialog.” The existing skill calls `coord_confirmation_probe` with no arguments. The tool prepares a synthetic project, `no_effect_check` action, revision, fresh public nonce and canonical hash; none refers to a real goal, rule or project. If the client advertises form elicitation, the default probe requests a form asking for that public nonce. Enter the nonce to test Accept; do not type `decline` or `cancel` into the nonce field. Those words are data, not protocol actions. Never enter a secret or let the agent answer for the user.

For “test Decline,” call `coord_confirmation_decline_probe` once with no arguments. It uses a separate fieldless, negative-only form and a synthetic `no_effect_decline_check` action; the nonce-entry probe and its validation are unchanged. In the [source-checked Codex release](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/tui/src/bottom_pane/mcp_server_elicitation.rs#L232-L324), a populated form submits content as protocol Accept, while a fieldless form offers **Allow / Deny / Cancel**. Select **Deny**, the second choice, and submit using the displayed selection controls to send protocol Decline. With default selection keys this is Down then Enter, or `2`; Esc sends Cancel, not Decline. Recheck the source/controls after host upgrades rather than generalizing a command-approval shortcut to a text-entry form.

The nonce form accepts only its displayed 36-character nonce. Submitting literal `decline` as nonce content is rejected by the SDK's accepted-content validation and produces `request_failed`; it does not prove a Decline action. The negative-only probe passes its requested observation only on `responseAction: "decline"` / `outcome: "declined_response"`; selecting Allow cannot count as a passed Decline check and never grants authority. If the expected Deny control is absent, report the host UI limitation rather than guessing or reinterpreting submitted text.

Every result has `humanVerified: false`, `authorityGranted: false` and `sideEffects: "none"`. Even a matching accepted response is only `accepted_response`, not human authentication or a backend approval. Client name/version and form/URL capability bits are self-reported observations. Other capability metadata, returned form fields and raw request errors are withheld. Undeclared form capability, a wrong/malformed answer, request failure or timeout leaves approval unavailable. The request is bounded to 90 seconds; host cancellation can end it earlier.

The probe does not call the backend, check in, renew a run, read a vault, register a host or synchronize files. The ordinary plugin exposes it through the already configured connection. A pre-existing run may continue its independent renewal timer. A missing tool requires reconnecting the upgraded MCP package, not creating credentials.

For isolated host diagnostics, use a temporary MCP configuration whose command is `coord` and arguments are `["mcp", "--confirmation-probe"]`. Use `coord mcp --confirmation-decline-probe` instead to serve only the negative-only tool for a targeted Decline check. Each isolated mode serves only its selected probe and bypasses project/runtime discovery even if runtime environment variables are present. The supporting CLI can also be launched with the built package's absolute `dist/src/cli.js` path from a temporary working directory. Do not install a global plugin, change persistent host settings or add a permission bypass for this experiment.

The isolated mode emits bounded `COORD_CONFIRMATION_PROBE` JSON observations on stderr: `prepared` means the synthetic request was prepared, not that a dialog was displayed; `completed` records the response or failure classification. A protocol callback, mock or automatically answered form does not prove visible UI or human participation. Actual host evidence must separately record negotiated capabilities, observed display, user choices and hook/automatic-answer behavior. This probe supplies no protected approval adapter.

## Protected approval

Approving a goal, capture policy or rule requires a protected human decision. The intended primary experience is review and approval from the host conversation through a qualified human-facing adapter, with credentials kept outside agent control. The currently implemented CLI fallback runs in a separate operator terminal, outside every agent or worker session, and reads the operator passphrase with hidden input only. Chat approval is not available merely because a host can show a form.

```text
coord approve goal <goal-id> --plan <plan.json> --vault <absolute-encrypted-vault> --revision <n> --hash <sha256-hex>
```

The command unlocks the existing encrypted vault without rewriting it or widening its binding, confirms the backend project is still the exact planned identity, and reads the named goal from project status. It then checks three things independently: the stated revision and hash are the project's current goal revision, the displayed content and limits reproduce that hash locally, and only a current draft revision is offered for approval. A mismatch is refused before anything is sent.

Only then does it display the effective backend project policy (allowed and excluded paths, rule targets, sharing approval, capture-policy digest, capacity, task cap and configuration/policy versions), then the goal's revision, hash, task limit, run timeout and full content, and require the operator to type the exact approval phrase. Goal content is proposed source data: it is shown with control characters escaped so it cannot emit terminal escapes or forge a confirmation line, and it carries no authority over the approval. Policy values use the same escaped display. This is the policy from the current status snapshot, not the potentially older setup plan; the goal hash does not bind it or prevent a later policy change. There is no flag that approves without that typed confirmation.

The mutation rebinds the exact revision and hash, so a revision proposed while the operator was reading is rejected rather than approved by the stale confirmation. If the reply to an approval is lost, running the same command again reports the already bound approval, including the recorded member and original server approval time (`approvedAt`, Unix epoch milliseconds), instead of approving a second time. An approval already bound to a different member is refused as a conflict rather than reported as this operator's, so one owner can never read another owner's approval as their own. Successful mutation replies must confirm the expected approver and a valid recorded approval time; missing or mismatched metadata produces no success report, even if the backend already applied the approval. Re-read status or rerun the exact command to recover that uncertain reply. Deploy the matching backend before using this command. Passphrases and credentials never appear in arguments, environment values, output or errors, and raw backend errors are never printed because they can carry the request credential.

### Capture-policy approval

```sh
coord approve policy <capture-policy.json> --plan <plan.json> --vault <absolute-encrypted-vault> --hash <sha256-hex>
```

The JSON file contains exactly the object used as `runtime.policy.capture`: `allowedUntracked`, `exclusions` (each with `path` and `reason`), `requiredPaths`, and optional `forbiddenContent` and `maxFileBytes`. Unknown keys, unsafe repository paths, invalid limits and unexplained duplicate exclusions are refused. The hash is `captureDigest(policy)`, SHA-256 of Coord's canonical JSON; ordinary file-byte SHA-256 is different. The file is read once and its validated contents must reproduce the stated hash before the vault passphrase is requested. No policy defaults are inserted into the approved object.

The command reuses the protected operator unlock without changing the plan or vault. It displays the full escaped capture policy, exact digest, current project settings and configuration/policy versions, then requires `approve policy <project-id> <sha256-hex>`. Declining makes no configuration request. `projects.configure` receives the effective current settings and only changes `capturePolicyDigest`; an expected configuration version rejects a concurrent configuration change instead of overwriting it. Deploy the matching backend with this optional version guard before using the command.

Successful configuration increments `configVersion` and `policyVersion`, invalidating existing machine qualification. The command checks the mutation response and reads status back to confirm the exact digest, preserved settings and resulting versions before printing success. An uncertain response or readback may follow an applied mutation; inspect status or rerun the same exact command. If that digest is already configured, the command reports the observed digest and versions with `mutated: false` without another confirmation or configuration write. This observation makes no claim about which operator previously approved it; projects do not store capture-policy approver metadata.

Keep the reviewed policy file under operator control and use that exact object in the protected runtime's `policy.capture`. This command does not write runtime files, edit the original setup plan or rebind its encrypted vault. Human review of the real policy and machine requalification remain separate operator actions.

### Rule approval

`coord approve rule` is the human-controlled boundary between an agent's proposed guidance and a mandatory project rule. Agents can record useful lessons or decisions without making them policy, and can explicitly propose a rule with evidence through `coord_record_memory` (`kind: "rule"`). Ordinary memories stay nonmandatory; this command approves only an existing proposed rule. It provides a protected way to use the encrypted human credential without extracting a token or pasting it into a dashboard or agent chat.

```sh
coord approve rule <memory-id> --plan <plan.json> --vault <absolute-encrypted-vault> --revision <n> --hash <sha256-hex>
```

For the currently implemented CLI fallback, a human executes this command in a separate operator terminal, outside agent and worker sessions. Agents may present proposals and request a protected human decision, but do not autonomously approve or receive the vault/passphrase; they propose and retrieve memories, then use qualified briefing and synchronization workflows. Enter the vault passphrase through hidden input. Neither an approval flag nor a model-authored instruction can replace the typed confirmation.

Use the ID, revision and hash of the rule being reviewed. The protected `memories.ruleForApproval` query reads exactly that project's full rule, including content, source task IDs/revisions/evidence references, applicability and confidence; it does not scan or truncate the approved-rule briefing to find proposals. The CLI independently recomputes SHA-256 of canonical `{kind, content, sources, applicability, confidence}` and refuses a mismatch before displaying a confirmation or sending an approval. The revision is checked separately. Proposed text and provenance are escaped source data, never instructions to the operator command.

After showing the full rule and its current project policy version, the command requires `approve rule <project-id> <memory-id> <revision> <hash>`. Declining leaves the rule proposed. `memories.approveRule` independently requires human authority, the exact proposed revision/hash and matching content hash; a change during confirmation is rejected. The resulting complete approved-rule set must fit the 12 KiB briefing bound, or approval fails with `COVERAGE_INCOMPLETE` instead of silently dropping mandatory rules.

Success reports the backend-recorded `approvedBy` and the rule's approval `policyVersion`, checked against an exact readback. Rule approval increments project `policyVersion` only: it leaves `configVersion` unchanged and does not invalidate machine qualification as a capture-policy configuration change would. Existing live sessions can fetch the new instructions and renew. New approvals also store server `approvedAt` on the rule; older records may lack it. The CLI reports its existing approver/policy-version receipt, while chat completion checks the recorded approval time.

If the approval reply or readback is uncertain, the backend may already have applied it even though no success is printed. Rerun the same exact command to read back the record. An active rule already bound to this operator and the same revision/hash returns its original recorded approver and rule policy version with `mutated: false`, without another confirmation or version increment. Another operator's approval is a conflict rather than reported as this operator's. Missing metadata, a different project/kind, stale content or an unavailable rule is refused. Deploy the matching exact-read query and approval reply before using this command.

Approval changes backend policy only. A fresh startup briefing or `coord_rules` reads the complete approved set; `coord rules sync` separately requires a qualified participating session and updates only its approved local targets, preserving human text outside `COORD:MANAGED:RULES:START/END`. It does not automatically edit files or synchronize every checkout. See the [learning workflow](../README.md#learning-and-rule-approval) for the human/agent handoff. The setup plan and encrypted vault are never rewritten or rebound by approval.

## Protected runtime selection

The schema lives in `src/command-runtime.ts`. Its fixed fields describe the trusted canonical repository root; private runtime state; fresh worktree root; machine/member; explicit trusted registry and project-agent credential-store references; canonical harness executable; capability key/evidence; separate artifact-verifier and supervisor credential **file references**; exact GitHub HTTPS transport; optional Linux cgroup-v2 containment; and capture/environment/setup/verification policy. It accepts no shell snippets, callback modules, dynamic runner plugins, approval switch or model-supplied verification/stop evidence.

Plain `coord mcp` is advisory intake only: it can review project rules/lessons, read project status and propose drafts, but never adopts legacy session grants, renews a run, or registers a model-selected host. Participating sessions start through qualified `resume`/daemon admission and the protected runtime bridge.

Keep the runtime file, state and privileged credential files outside all worker trees. File modes reduce accidental disclosure; actual native filesystem/helper isolation must be independently tested. The CLI compares runtime evidence with the owner-provisioned backend machine record, checks current project configuration/expiry, and probes actual OS/release/architecture, adapter/probe and selected harness version. Merely copying a file and adding PASS rows does not qualify a machine. The protected runtime is re-read at operation/launch renewal boundaries. HOME paths must be canonical; copied application environment names cannot override HOME, PATH or coordinator/loader/Git controls. Configuration digests bind the client and fixed runtime/transport/containment/verification adapter versions plus policy and source references, never credential contents or copied application secret values. Installed coordinator/MCP code and external harness/permission configuration must remain protected and require requalification when changed. Same-path executable version output does not prove arbitrary external settings are unchanged.

The trusted stdio MCP server exposes bound checkpoint, review, finalization and replanning actions with ID/proposal-only schemas. Runtime/session/credential paths and independent attestations are not model tool arguments. `coord mcp --runtime <protected-file> --session <id>` binds them at startup; dedicated worker HOME requires no copied owner/provider credentials or account configuration. Fresh Codex launch supplies fixed MCP-server command/argument overrides for the installed CLI. Other qualified plugins can inherit nonsecret `COORD_RUNTIME_PATH` and `COORD_SESSION_ID`; the owner must prove actual protected `mcp.runtime-actions` wiring. Every callback retains its startup grant/identity and rechecks the exact routing/session/worktree receipt rather than rereading an interchangeable grant at effect time. Stateless hook and rule-sync processes also honor the bound `COORD_RUNTIME_PATH` and explicit registry/store references under a dedicated HOME; accepted-result hooks remain write-blocking. The actual installed `coord` hook command must be reachable through the selected protected worker PATH and pass discovery/delivery qualification. `policy.verification.searchPath` can select a separate narrow immutable toolchain PATH for isolated tests; it defaults to the worker search path when omitted.

The fixed Git transport binds `github-https`, the exact approved `https://github.com/<owner>/<repo>.git` URL, a canonical protected `gh` executable, dedicated protected provider HOME and explicit helper search path. Git runs with a sanitized environment, blocked ambient proxies/loaders, fixed credential-helper invocation, no interactive authentication, no submodule recursion and rejected execution-bearing local configuration. The official helper resolves its approved authentication normally; Coord does not read or print raw GitHub account credentials. Production network operations cannot fall back to ambient Git authentication. SSH/custom Git transports are not supported by this command path.

The runtime's capture policy must hash to the protected project's approved `capturePolicyDigest`. The live pilot currently has no such approval. The current project changed-path policy excludes `seeds/`, which already exists in the published baseline. A future explicitly reviewed capture policy may retain those unchanged already-remote blobs while forbidding modifications. A policy that removes them instead creates deletions requiring explicit scoped approval. Neither option has been selected by this implementation; the current blocker is the missing exact human-approved capture policy, not an inherently unusable baseline.

## Actual operation sequencing

Checkpoint requires a current participating run and real recorded progress. It records stable request IDs, creation time, execution base, progress revision/hash and manifest before external effects. It captures the complete audited portable tree, submits preparation with the exact canonical progress summary, computes/uploads the complete actual diff, and obtains independent scope verification **before any Git push**. Only then does it publish the immutable safe snapshot, independently fetch/read its exact code/parents, and request ready acceptance. A prepared artifact or successful push alone is never called ready. Same-ID retries reuse durable state; changed content/configuration is rejected.

Resume selects an explicit latest ready checkpoint or a positively permitted initial base. It verifies the exact remote artifact and preflights environment/lockfile setup requirements from that immutable code before admission. The project-agent approved-rules query also composes the full mandatory startup briefing with the selected goal/task, immutable progress and exact dependency pins, reserving conservative identity/restore overhead before any claim. Oversized unchanged context therefore creates no epoch or claim/refund loop. The post-admission briefing is checked again for concurrent changes. Admission request, run grant and launch ID are persisted before the transaction. A fresh epoch/run branch is allocated without resetting any existing directory. Exact code, remote, common Git directory and admitted run are rechecked, and only the scoped run session is installed. Interrupted allocation with unknown effects remains inspectable instead of being guessed safe. A proven prelaunch failure can settle only the exact unused managed reservation through separate supervisor authority.

Declared published dependencies are selected by immutable checkpoint ID. Preflight retrieves each exact historical input manifest/summary in a bounded individual query, fetches/verifies its exact ref/commit/tree, and refuses missing refs or failed/unavailable prerequisites before claim. A newer neighboring latest checkpoint never replaces a pin. The startup briefing and `coord_dependency_input` expose compact exact code references; no input is automatically merged.

The checkpoint's immutable summary supplies restored progress. Later source progress without a matching checkpoint is explicitly marked as unavailable in `.coord-local/resume.json`. After exact reconstruction, a manual run updates its authoritative progress to the selected checkpoint; a managed run does so only after launch authorization and before wrapper release. A source-local journal is unnecessary for reconstruction. The new session starts with a bounded goal/task/checkpoint/rule briefing and the installed participating session ID. Default resume actually starts the selected fresh harness; `--prepare-only` explicitly requests allocation without launching. A launch journal prevents blind respawn. Manual direct-child exit revokes only its registration and makes no descendant-stop or managed-capacity claim.

Review requires this run's ready artifact. The trusted verifier materializes and tests the final immutable head/tree in an independently qualified native sandbox, with explicit approved commands and no provider/approval/verifier/supervisor credentials in child arguments/environment or readable mounts. Verification is bound to that head/tree, current target base and effective environment. The safe PR helper uses an independent publication ID, immutable review branch, exact Git/PR readback and durable host reconciliation. Backend branch/PR verification and acceptance remain separate. A lost acceptance response can reconcile the same verified artifact through the verifier while the run remains authorized; it does not create another PR. A restarted trusted MCP can recover an accepted current run in cleanup-only mode: ordinary writes and renewal stay closed, while exact review reconciliation/finalization remain backend-authorized. Accepted publication never releases process capacity.

Finalization freezes ordinary execution. A manually participating registration is revoked without pretending its parent process stopped. Managed finalization uses the separately authenticated supervisor and requires positive exact process-tree stop evidence before capacity release. A wrapper receipt whose launch authorization was denied can be registered only as terminal evidence together with positive stop proof; it never starts a run or renews a lease. The complete whitelisted stop request is persisted and replayed unchanged. Unknown launch/stop identities preserve holds; old results cannot resurrect a newer run. The explicit `run reconcile` command reads a route/runtime-bound launch envelope and scoped supervisor status, reconciles saved exit/unused-launch receipts, or independently observes the exact recorded cgroup. `--stop` permits stopping that exact known containment. Unknown/prepared records retain holds; no process is respawned. Original backend-verified lifecycle provenance is persisted before launch. Physical stop/observation of that already owned containment uses its protected historical ownership and current kernel identity even during a backend outage; a cleanup-only controller cannot prepare, attach or authorize a new launch. Positive exit proof is written locally before any supervisor handshake/RPC.
