# Checkpoint, continuation and runtime commands

These commands compose the existing Convex, Git, capture, worktree, verification and supervisor modules. They require a protected runtime configuration and independently owner-provisioned machine evidence. The connected private taskboard is not qualified for these execution modes yet: no machine, goal or capture policy has been approved for it. Do not create synthetic qualification records to make these commands run on the live deployment.

```text
coord checkpoint <checkpoint-id> --runtime <protected-runtime.json> --session <session-id>
coord resume <task-id> --runtime <protected-runtime.json> --session <new-session-id>
coord resume <task-id> --checkpoint <ready-id> --runtime <protected-runtime.json> --session <new-session-id>
coord resume <task-id> ... --prepare-only
coord review <publication-id> --checkpoint <ready-id> --runtime <protected-runtime.json> --session <session-id>
coord run finalize succeeded|failed|stopped --runtime <protected-runtime.json> --session <session-id>
coord run reconcile <launch-id> --runtime <protected-runtime.json> [--stop]
coord daemon --runtime <protected-runtime.json>
coord daemon --runtime <protected-runtime.json> --check
```

`--harness codex|antigravity` may confirm a resume selection; it cannot change the qualified executable/configuration. Session and operation IDs are nonsecret correlation values. Credentials and operator passphrases never belong in arguments or environment variables. Run grants are installed in private, backend-URL-bound session receipts. Worker credentials, lifecycle supervisors and artifact verifiers remain separate roles.

## Protected approval

Approving a goal is an owner action. It runs in a separate operator terminal, outside every agent or worker session, and reads the operator passphrase with hidden input only.

```text
coord approve goal <goal-id> --plan <plan.json> --vault <absolute-encrypted-vault> --revision <n> --hash <sha256-hex>
```

The command unlocks the existing encrypted vault without rewriting it or widening its binding, confirms the backend project is still the exact planned identity, and reads the named goal from project status. It then checks three things independently: the stated revision and hash are the project's current goal revision, the displayed content and limits reproduce that hash locally, and only a current draft revision is offered for approval. A mismatch is refused before anything is sent.

Only then does it display the goal's revision, hash, task limit, run timeout and full content, and require the operator to type the exact approval phrase. Goal content is proposed source data: it is shown with control characters escaped so it cannot emit terminal escapes or forge a confirmation line, and it carries no authority over the approval. There is no flag that approves without that typed confirmation.

The mutation rebinds the exact revision and hash, so a revision proposed while the operator was reading is rejected rather than approved by the stale confirmation. If the reply to an approval is lost, running the same command again reports the already bound approval, including the member it is bound to, instead of approving a second time. An approval already bound to a different member is refused as a conflict rather than reported as this operator's, so one owner can never read another owner's approval as their own. Passphrases and credentials never appear in arguments, environment values, output or errors, and raw backend errors are never printed because they can carry the request credential.

## Protected runtime selection

The schema lives in `src/command-runtime.ts`. Its fixed fields describe the trusted canonical repository root; private runtime state; fresh worktree root; machine/member; explicit trusted registry and project-agent credential-store references; canonical harness executable; capability key/evidence; separate artifact-verifier and supervisor credential **file references**; exact GitHub HTTPS transport; optional Linux cgroup-v2 containment; and capture/environment/setup/verification policy. It accepts no shell snippets, callback modules, dynamic runner plugins, approval switch or model-supplied verification/stop evidence.

Plain `coord mcp` is advisory intake only: it can read project status and propose drafts, but never adopts legacy session grants, renews a run, or registers a model-selected host. Participating sessions start through qualified `resume`/daemon admission and the protected runtime bridge.

Keep the runtime file, state and privileged credential files outside all worker trees. File modes reduce accidental disclosure; actual native filesystem/helper isolation must be independently tested. The CLI compares runtime evidence with the owner-provisioned backend machine record, checks current project configuration/expiry, and probes actual OS/release/architecture, adapter/probe and selected harness version. Merely copying a file and adding PASS rows does not qualify a machine. The protected runtime is re-read at operation/launch renewal boundaries. HOME paths must be canonical; copied application environment names cannot override HOME, PATH or coordinator/loader/Git controls. Configuration digests bind the client and fixed runtime/transport/containment/verification adapter versions plus policy and source references, never credential contents or copied application secret values. Installed coordinator/MCP code and external harness/permission configuration must remain protected and require requalification when changed. Same-path executable version output does not prove arbitrary external settings are unchanged.

The trusted stdio MCP server exposes bound checkpoint, review, finalization and replanning actions with ID/proposal-only schemas. Runtime/session/credential paths and independent attestations are not model tool arguments. `coord mcp --runtime <protected-file> --session <id>` binds them at startup; dedicated worker HOME requires no copied owner/provider credentials or account configuration. Fresh Codex launch supplies fixed MCP-server command/argument overrides for the installed CLI. Other qualified plugins can inherit nonsecret `COORD_RUNTIME_PATH` and `COORD_SESSION_ID`; the owner must prove actual protected `mcp.runtime-actions` wiring. Every callback retains its startup grant/identity and rechecks the exact routing/session/worktree receipt rather than rereading an interchangeable grant at effect time. Stateless hook and rule-sync processes also honor the bound `COORD_RUNTIME_PATH` and explicit registry/store references under a dedicated HOME; accepted-result hooks remain write-blocking. The actual installed `coord` hook command must be reachable through the selected protected worker PATH and pass discovery/delivery qualification. `policy.verification.searchPath` can select a separate narrow immutable toolchain PATH for isolated tests; it defaults to the worker search path when omitted.

The fixed Git transport binds `github-https`, the exact approved `https://github.com/<owner>/<repo>.git` URL, a canonical protected `gh` executable, dedicated protected provider HOME and explicit helper search path. Git runs with a sanitized environment, blocked ambient proxies/loaders, fixed credential-helper invocation, no interactive authentication, no submodule recursion and rejected execution-bearing local configuration. The official helper resolves its approved authentication normally; Coord does not read or print raw GitHub account credentials. Production network operations cannot fall back to ambient Git authentication. SSH/custom Git transports are not supported by this command path.

The runtime's capture policy must hash to the protected project's approved `capturePolicyDigest`. The live pilot currently has no such approval. The current project changed-path policy excludes `seeds/`, which already exists in the published baseline. A future explicitly reviewed capture policy may retain those unchanged already-remote blobs while forbidding modifications. A policy that removes them instead creates deletions requiring explicit scoped approval. Neither option has been selected by this implementation; the current blocker is the missing exact human-approved capture policy, not an inherently unusable baseline.

## Actual operation sequencing

Checkpoint requires a current participating run and real recorded progress. It records stable request IDs, creation time, execution base, progress revision/hash and manifest before external effects. It captures the complete audited portable tree, submits preparation with the exact canonical progress summary, computes/uploads the complete actual diff, and obtains independent scope verification **before any Git push**. Only then does it publish the immutable safe snapshot, independently fetch/read its exact code/parents, and request ready acceptance. A prepared artifact or successful push alone is never called ready. Same-ID retries reuse durable state; changed content/configuration is rejected.

Resume selects an explicit latest ready checkpoint or a positively permitted initial base. It verifies the exact remote artifact and preflights environment/lockfile setup requirements from that immutable code before admission. The project-agent approved-rules query also composes the full mandatory startup briefing with the selected goal/task, immutable progress and exact dependency pins, reserving conservative identity/restore overhead before any claim. Oversized unchanged context therefore creates no epoch or claim/refund loop. The post-admission briefing is checked again for concurrent changes. Admission request, run grant and launch ID are persisted before the transaction. A fresh epoch/run branch is allocated without resetting any existing directory. Exact code, remote, common Git directory and admitted run are rechecked, and only the scoped run session is installed. Interrupted allocation with unknown effects remains inspectable instead of being guessed safe. A proven prelaunch failure can settle only the exact unused managed reservation through separate supervisor authority.

Declared published dependencies are selected by immutable checkpoint ID. Preflight retrieves each exact historical input manifest/summary in a bounded individual query, fetches/verifies its exact ref/commit/tree, and refuses missing refs or failed/unavailable prerequisites before claim. A newer neighboring latest checkpoint never replaces a pin. The startup briefing and `coord_dependency_input` expose compact exact code references; no input is automatically merged.

The checkpoint's immutable summary supplies restored progress. Later source progress without a matching checkpoint is explicitly marked as unavailable in `.coord-local/resume.json`. After exact reconstruction, a manual run updates its authoritative progress to the selected checkpoint; a managed run does so only after launch authorization and before wrapper release. A source-local journal is unnecessary for reconstruction. The new session starts with a bounded goal/task/checkpoint/rule briefing and the installed participating session ID. Default resume actually starts the selected fresh harness; `--prepare-only` explicitly requests allocation without launching. A launch journal prevents blind respawn. Manual direct-child exit revokes only its registration and makes no descendant-stop or managed-capacity claim.

Review requires this run's ready artifact. The trusted verifier materializes and tests the final immutable head/tree in an independently qualified native sandbox, with explicit approved commands and no provider/approval/verifier/supervisor credentials in child arguments/environment or readable mounts. Verification is bound to that head/tree, current target base and effective environment. The safe PR helper uses an independent publication ID, immutable review branch, exact Git/PR readback and durable host reconciliation. Backend branch/PR verification and acceptance remain separate. A lost acceptance response can reconcile the same verified artifact through the verifier while the run remains authorized; it does not create another PR. A restarted trusted MCP can recover an accepted current run in cleanup-only mode: ordinary writes and renewal stay closed, while exact review reconciliation/finalization remain backend-authorized. Accepted publication never releases process capacity.

Finalization freezes ordinary execution. A manually participating registration is revoked without pretending its parent process stopped. Managed finalization uses the separately authenticated supervisor and requires positive exact process-tree stop evidence before capacity release. A wrapper receipt whose launch authorization was denied can be registered only as terminal evidence together with positive stop proof; it never starts a run or renews a lease. The complete whitelisted stop request is persisted and replayed unchanged. Unknown launch/stop identities preserve holds; old results cannot resurrect a newer run. The explicit `run reconcile` command reads a route/runtime-bound launch envelope and scoped supervisor status, reconciles saved exit/unused-launch receipts, or independently observes the exact recorded cgroup. `--stop` permits stopping that exact known containment. Unknown/prepared records retain holds; no process is respawned. Original backend-verified lifecycle provenance is persisted before launch. Physical stop/observation of that already owned containment uses its protected historical ownership and current kernel identity even during a backend outage; a cleanup-only controller cannot prepare, attach or authorize a new launch. Positive exit proof is written locally before any supervisor handshake/RPC. Backend capacity settlement waits for valid supervisor authentication and reconnect/replay, independently of revoked worker/project-agent grants. Existing journals and locks require explicit inspection when automatic reconciliation lacks positive evidence.

Daemon uses the official Convex client's subscription to runnable work. It applies the same exact-code/environment preflight and durable admission/worktree flow, then the qualified wrapper/supervisor and finalization path. The wrapper self-attaches to selected Linux cgroup-v2 containment before receipt/authorization; no arbitrary PID migration or process-group-as-sandbox shortcut exists. Supplemental cgroup control-path isolation evidence is required. `--check` performs query-only candidate/admission diagnostics and cannot reserve capacity or start a model.

## Supported limits and verification status

- Current macOS execution/verification remains unsupported until the required native controls are demonstrated. Selecting `macos-sandbox-exec` reports a blocker; its presence is not parent-death containment evidence. There is no fallback to an ordinary unprotected test subprocess.
- Linux verification supports an explicitly selected, already installed, qualified system bubblewrap with private namespaces and read-only source; nothing is installed automatically. Runtime tests exercise fixed file/environment/network/containment canaries. No app/provider environment requirements are silently omitted: the current offline verifier blocks configurations requiring them.
- Nonempty dependency setup is blocked before admission until an independently isolated setup adapter exists. The taskboard has no dependencies and needs no install. Install scripts are never executed in the privileged account as an assumed harmless setup step.
- Codex replanning uses fixed `exec --json --sandbox read-only` arguments only when the backend owner provisioned a current real `harness.replan-readonly` all-tool/native qualification bound to the same runtime. Help/version output proves flag availability only. Missing proof and Antigravity replanning are rejected before claim; backend artifact denial is an additional guard.
- Trusted runtime/MCP/daemon/operator processes can call the same direct orchestration functions; no compulsory local IPC broker is introduced. A worker must not receive privileged runtime credentials to run a helper. The eventual qualified host must provide a tested protected helper invocation boundary; ordinary file permissions do not establish it.

The actual private taskboard's ordinary six store/HTTP tests passed separately after a narrowly permitted loopback-listening run; the restricted sandbox first reported `listen EPERM`. Root separately verified an operator-account `refs/coord/probes/` create-only ref pointing only to already published main. That namespace probe is not worker authentication, isolated Git permissions, checkpoint readiness or a new code publication.

The command rehearsals use disposable copies of the real taskboard, bare Git remotes, the official HTTP wire format against exported backend handlers, fixed subprocess transports and clearly synthetic qualification/host/sandbox inputs. They exercise checkpoint/replay, source-offline exact continuation, fresh harness startup, scope rejection before push, environment blockers, publication reconciliation and capacity separation. Actual taskboard unit/HTTP tests run separately. Simulated sandbox or GitHub responses are not native containment, provider authentication, live Convex concurrency, two-machine acceptance or A1–A7 proof. No live taskboard refs or PRs are published by these tests.
