# Backend implementation and qualification boundary

The `convex/` modules export real Convex 1.49.0 query, mutation, internal mutation and cron definitions. `server.ts` derives their types directly from `schema.ts`; a deployment and generated API files are unnecessary for local compilation. No deployment/admin key belongs in an agent, plugin or worker environment.

`tests/backend.test.ts` invokes those exported handlers using `backend.fixture.ts`, which serializes transactions and restores writes on failure. This proves deterministic guards and state transitions. It does **not** exercise Convex's real optimistic concurrency, a deployed subscription, real human unlock, credential isolation, Git-host verification or two machines. The synthetic qualification records in those tests are explicitly fixture inputs, not evidence that any host passed qualification. Real Stage 1 ownership contention and A1–A7 remain blocked until the operator provisions and qualifies the selected environment.

## Identity, credentials and exact approval

Every ordinary public request supplies `token`, `backendId`, `projectId`, `protocolVersion`, `clientVersion`, `capabilities` and a stable `requestId`. Run calls also supply `taskId`, `runId`, `epoch` and `goalRevision`. Server time controls expiry. Authentication checks credential digest, backend/project membership, revocation, expiry, role, both directions of protocol/capability compatibility and writer migration state before replay.

All credentials and invitation values must use independent random 32-byte values encoded as 64 lowercase hexadecimal characters. Callers generate these using platform cryptographic randomness. Convex stores SHA-256 digests only; tokens are absent from results, audit detail and exports. Request payloads are canonically hashed, including secret-bearing input fields when necessary, but raw payloads are not stored. `auth.bootstrap` and `machines.provisionQualification` are **internal only** deployment-owner operations. Bootstrap accepts only `humanDigest`/`agentDigest`, never plaintext credential arguments; the external operator seals the random credentials in a durable encrypted vault before calling it. Exact retry is allowed only while the entire original metadata/project/active credential state still matches. Qualification provisions separate machine/project/member-bound `supervisor` and `artifact_verifier` credentials from independently supplied owner-only secret inputs. No public wrapper, MCP tool, TTY check, model-authored approval flag or plaintext unlock substitutes for a protected human facility. That facility remains an external qualification gate.

`auth.invite` requires human authority, permits only that approver's existing project scope and expires within 24 hours. `auth.redeem` is the narrow bootstrap exception: a one-use invite atomically creates the independently supplied credential. Known-invite invalid attempts are capped at five. Every redemption attempt, including unknown tokens and malformed credential formats, also consumes a server-time fixed-window deployment-wide budget of 60 attempts per minute. The singleton key is chosen by backend code, independent of caller-supplied backend/project/token values. Denials are returned as data so counter writes commit rather than roll back. Exhausting this anonymous budget temporarily denies legitimate joins too; the next minute resets it, and ordinary authenticated operations are unaffected. This application throttle is not a replacement for platform transport/abuse controls. A guessed unknown 256-bit invite returns a uniform denial without a record lookup result. Replay of a redeemed invitation checks the newly provisioned credential's digest, revocation and expiry before returning its stored receipt.

`goals.propose` hashes canonical `{content, taskLimit, runTimeoutMs}`. `goals.approve` requires the exact draft revision/hash and human role. `goals.control` pauses/cancels and revokes owned runs without releasing supervised capacity. `goals.resume` permits only the exact previously approved paused revision. Cancellation cannot resume.

`projects.configure` is a human operation for sharing, path policies, capture-policy digest and limits. Repository rerouting requires a separate project and protected local trust setup. `configVersion` changes invalidate machine/run qualification; `policyVersion` identifies approved rules. Rule approval changes only `policyVersion`, so existing live sessions can fetch new instructions and renew. `memories.rules` also returns authoritative `ruleTargets` for local target validation.

## Admission and leases

`tasks.propose` appends an in-scope task to the approved goal. Existing-only dependency edges cannot introduce a new-task cycle. Run-scoped `tasks.proposeSubtasks` additionally validates the complete bounded replacement graph, goal/task caps and all children before any child becomes visible.

`tasks.registerManual` and `tasks.claim` share common admission input plus `taskId`, `runId`, `launchId`, `grantToken`, `machineId`, `harness` and the exact current `capabilityKey`. Both require independently provisioned real, fresh, configuration-bound qualification; fixtures and missing checks fail closed. Manual participation is separately visible and does not consume a managed capacity reservation. A managed claim checks project and machine reservations transactionally, reserves the task's exclusive declared scope, increments its epoch and stores only the new grant digest. The result never includes `grantToken`.

`tasks.renew`, `tasks.progress`, `tasks.checkIn` and other run operations check the authenticated run grant, member/project/task/run/epoch, owner pointer, live lease/deadline, allowed transition, current approved goal, current sharing/scope and unchanged qualified configuration. A project agent cannot supply an epoch to impersonate a run. Mutable work cannot proceed while finalizing or after review readiness.

`lifecycle.starting` precedes spawn. `lifecycle.authorizeLaunch` is supervisor-only, rechecks the full current run grant/configuration/member/mode authority and binds the registered process identity to the exact launch before authorizing the harness. Supervisor credentials are scoped separately to machine/project/member and lifecycle evidence operations only; revoking a worker does not prevent eventual exit reporting. A supervisor cannot approve a goal, mandatory rule, trusted scan, checkpoint readiness or publication. Artifact verifiers cannot release process capacity.

## Coordination and bounded reads

`scans.upload` accepts at most 500 paths and 100 KiB per chunk, validates the canonical path-list digest, exact source HEAD/tree and expected totals, and marks a revision transmission-complete only when every chunk is present without duplicate paths. Every path must remain inside the task's reserved scope. An explicitly empty scan is one empty chunk with expected path count zero. Worker uploads never mark task coverage complete. `scans.verify`, callable only by an artifact verifier or human, compares the complete uploaded path set with an independently observed actual Git scan using exact count, sorted canonical path digest, source HEAD/tree and epoch. It records the trusted scan marker and only then marks coverage complete. Progress changes invalidate coverage, and publication requires the completed scan to match its exact captured source HEAD/tree. There is a bounded 1,000-chunk maximum; unsupported larger data fails explicitly rather than being silently dropped.

`messages.send` binds sender and recipient epochs. Receipts distinguish bridge delivery, offering bytes, injection and explicit agent acknowledgement. Receipt retries do not resolve conflicts. Declined, escalated, unanswered and stale decisions do not permit admission/publication. An accepted resolution names the current sender and recipient epochs. `messages.resolveBeforeAdmission` is a human-only escape from a queued-task conflict deadlock and binds exactly the next recipient admission epoch. It does not clear an uncertain launch.

`messages.read` and `memories.context` accept an optional opaque Convex `cursor` and return `nextCursor`, byte accounting and explicit `complete`. Single-record pages preserve IDs even when records require expansion. Message bodies/decisions and memory content/provenance can be fetched with bounded `expand` calls. Offsets cannot split Unicode code points. `tasks.checkIn` returns an authoritative `conflictBlocked` flag independent of what fits in the routine message budget.

Ordinary lessons and decisions carry sources, applicability and confidence. Proposed rules remain proposed until exact human approval. Mandatory-rule queries use a separate index, so a long lesson history cannot hide rules. Rule approval checks that the resulting complete approved set fits the 12 KiB briefing bound. Retrieved ordinary source text is explicitly untrusted data. Local rule-file synchronization remains the CLI's responsibility and must preserve human-authored content.

## Checkpoints and PR publication

Implementation workers may call `checkpoints.prepare`, using the complete typed capture manifest. Replanning runs cannot prepare, verify or accept code artifacts. Preparation validates exact run identity, pinned execution base, current progress hash/revision, file types/modes/identities, bounds and canonical manifest digest. `checkpoints.authority` exposes the current progress/base identity for local capture validation; its policy digest comes from protected project configuration.

Only a scoped artifact verifier or human can call `checkpoints.verifyCode` and `checkpoints.ready`. Verification binds remote readback to the immutable commit/tree/ref/manifest/progress, approved capture-policy digest and actual parent list. A new snapshot has exactly one parent: the verified execution base. An unchanged reused base records its actual parents; it never claims that a commit is its own parent. Ready acceptance rechecks current goal, lease, epoch, configuration, progress, policy and the trusted exact-source/tree scan before updating the task pointer. The scan evidence is preserved in the ready manifest. Project-agent `checkpoints.getReady` returns an explicit `ready` artifact/manifest/summary or `initial_base`; it never treats a missing checkpoint as evidence that prior execution made no changes.

`publications.request` permits only a ready audited snapshot and passing verification on the **final** review head/tree and relevant target base. Replanning runs cannot publish implementation code. `verifyBranch`, `verifyPR` and `accept` require independent artifact-verifier or human authority, reopen the ready checkpoint manifest and revalidate current progress, capture policy and immutable artifact. PR evidence binds exact repository identity, immutable head branch, configured target branch and current base SHA. Acceptance records `review_ready` and the accepted result; it does not free capacity.

These mutation arguments are evidence attestations from a separately scoped trusted artifact verifier. A lifecycle supervisor is not an artifact verifier. Convex does not independently perform Git fetches or provider API reads inside a mutation. The local verifier must actually perform and qualify those operations, keep its credential inaccessible to worker tools and preserve the referenced evidence. The local handler fixtures are not proof of these external effects.

## Finalization, yielding, replanning and recovery

`lifecycle.requestFinalization` freezes implementation/publication. Successful code execution requires an accepted verified PR; failure never manufactures success. Manual registration revocation clears that exact registration's task ownership and lease without claiming that its parent harness stopped; a subsequent run still requires an explicit ready checkpoint or positive never-started evidence. Managed capacity is released only by `confirmStopped` with positive evidence for the owned process tree, proven never-started launch, or verified changed boot identity. Missing PID matches and unconfirmed stop requests retain capacity and a task-wide hold. Exact retries return the original release receipt. Late evidence settles only its own reservation; a paused/cancelled goal or newer epoch cannot be resurrected.

Prerequisite children are created with dispatch held. `requestYield` requires the parent's ready checkpoint matching its current progress, then freezes the parent. Only positive stop confirmation releases its slot, exposes those children and sets `waiting_dependencies`. A failed checkpoint or stop leaves the hold intact.

A durable 60-second bounded expiry cron revokes expired credentials and runs. Retired terminal rows are removed from the expiry range so they cannot starve later work. Unknown launch/failed-stop reservations remain held. A separate bounded dependency sweep uses durable scheduled cursor continuation, so waiting work wakes without a coordinator model polling. Published dependencies bind exact ready artifacts. Terminal failed/cancelled prerequisites produce one `replan_requested` transition. `claimReplan` bypasses the old failed prerequisites but consumes ordinary managed capacity and increments a persistent two-attempt limit. `finishReplan` accepts an in-scope revised DAG or blocked/failed decision, then requires positive stop evidence without creating a dummy PR. That stop atomically releases the revised DAG's required held children; unrelated held children remain held.

`tasks.requestResume` requeues eligible blocked work only after its reservation is settled and an explicit matching latest ready checkpoint is selected. Checkpoint-free retries require positive `proven_never_started` evidence from the exact previous settled attempt; a zero progress revision is insufficient. Fresh first admission may reconstruct its approved base before launch. Human force-clear is a distinct, audited override: it advances authority but explicitly does not prove process death or refunded usage. It does not silently resume the task.

## Remaining gates and limits

- Development deployment, live argument-validation/auth rejection probes and empty maintenance mutations passed. Operator bootstrap/connect is complete. Real OCC contention/subscription tests, protected-human unlock/isolation qualification and the two-machine pilot remain unqualified.
- Merged dependency admission is deliberately unsupported until independent observed integration evidence is implemented. It fails closed; an open PR never counts as merged.
- Scope and scan validators verify declared bounded data. The complete real scanner/capture/provider path and its evidence must be exercised against actual repositories before qualification.
- Expiry recovery conservatively preserves a supervised reservation until positive stop evidence or explicit human override. It does not infer that a disconnected process stopped consuming provider resources.
- No agent merge/deploy operation exists. Git-host/native credential isolation and actual merge/deploy restrictions remain required host qualification, not a consequence of ref names or backend RBAC.
