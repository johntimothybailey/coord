# OAuth authority foundation

Coord's primary experience is conversational: ask the connected agent to show project status, review proposed rules or lessons, propose source-backed guidance, or request exact rule approval. The scoped remote MCP endpoint at `/mcp` forwards these operations to the existing domain functions. A request to approve returns the existing request binding and status; the protected passkey workflow remains the only browser rule-decision authority. OAuth grants never confer a human role. Existing stdio tools and protected terminal fallbacks remain available.

This is backend infrastructure, not a delivered Connect workflow. No sign-in method or Connect UI is configured. The `mcpConsent.getAuthRequest` query and SDK-backed `mcpConsent.authorize` action provide browser authorization APIs, both gated on a live enabled application identity; subsequent project `consentGrant` remains mandatory. A protected human-facing integration must supply the sign-in method and consent UI before advertising connection setup. Configure `COORD_OAUTH_CONSENT_URL` with that facility's HTTPS URL; without it, the OAuth authorization route returns an explicit unavailable response. Do not point it at an agent-controlled page. Native plugin delivery, browser issuance, human provisioning, isolation, live races and capacity are unqualified by offline tests.

## Identity and project consent

Convex Auth v2 owns browser sessions; application `users` records own enablement. A future sign-in method must attach the internal identity-only `oauthAuthority.createUser` callback using Auth v2's `{method: {name, profile}}` contract. Registration creates no membership, human role or project authority. Profile names and email addresses are not authorization identifiers.

A deployment owner uses the internal `installLink` operation to preinstall an exact user, existing legacy agent source, backend, single project, scope ceiling and immutable generation. This operation is not an MCP tool, public function or HTTP endpoint; its protected human provisioning facility still requires separate qualification. An authenticated browser activates that exact installed generation using `activateLink`, then uses `consentGrant` to associate its exact current OAuth grant with the installed project. The server derives the user from the current Auth session, not request arguments. A link selector alone grants nothing.

The SDK authorization action authenticates browser identity before delegating to the component; that earlier lookup does not serialize component issuance with subsequent application membership changes. An unbound component grant confers no Coord access. The project consent, binding and domain mutations recheck current authority in their transactions.

Consent is an immutable grant-to-project association. The same grant cannot switch projects, sources or generations. Replacement installs a new link generation and revokes prior generations. Revoked connection and link records remain tombstones; do not delete them to permit reassignment. Activation or consent retries return only while the same current authority remains valid. This slice does not deliver workspace switching or onboarding UI.

Auth v2 resolves browser identity through the platform-verified JWT and the component's current session row, then Coord checks enabled application authority. The pinned component's `getSession` checks row existence; it does not independently compare maximum or inactivity timestamps. Refresh and cleanup enforce those session lifetimes through removal. Immediate timestamp enforcement before removal, JWT signature/expiration verification and actual browser issuance are not established by the offline fixtures, and this integration selects no additional browser-session duration policy.

## Bearers and children

After browser project consent, `oauthAuthority.bind` establishes the agent root. Every root request supplies the explicit `oauthBearer` field and an empty legacy `token` field. The legacy 64-hex path remains separate; it cannot use an OAuth root without its current bearer. `BackendClient(config, bearer, "oauth")` supplies this routing for programmatic callers; `withRunToken` returns to the legacy-format child-token transport with mandatory server-side lineage checks. Tokens are excluded from idempotency payloads and audit records.

Every bearer use calls the installed MCP component's query-safe `tokens.verify` with current server time, including in the final domain query or mutation transaction. Raw bearers are never retained for children. The HTTP ingress uses a request-local closure to forward the actual bearer, rather than trusting SDK user metadata. Read-only review never requires a telemetry mutation. Scope names restrict the existing five-role permissions; an explicit server operation map denies unknown, human-only, export and dispatch operations.

The immutable connection cap is the original component grant creation timestamp plus 24 hours, intersected with the installed source, link and membership limits. Refresh, rebinding, admission and renewal cannot reset or extend it. The supported `grants.list` API exposes only the newest 200 grants. If the exact grant is missing, truncated or unavailable, authorization denies; this is an availability limit, not proof of deliberate revocation.

Admitted runs and owner-provisioned supervisor/verifier children carry their immediate parent, connection, scopes and ceiling. Every operation intersects current application enablement, link/membership generation, original source agent, grant, all ancestors, scopes and local lifetimes. Children may continue across normal access-token expiry and rotation while those authorities and their ordinary run lease remain valid. Disconnect, source revocation, membership removal, user disablement, scope narrowing or cap expiry denies the next operation without waiting for cleanup. Launch and artifact acceptance separately check the target run's lineage, including when the supervising/verifying caller has other valid authority. Cleanup can still record uncertainty or proven termination without authorizing execution.

The existing 20-second renewal, 90-second lease, 60-second watchdog/sweep and ordinary run timeout remain unchanged. Historical legacy credentials retain their existing compatibility path; no retirement or forced backfill is introduced. Protected rule approvals, enrollment, recovery and human-only goal/policy operations retain their gates.

## Retry and verification limits

Keep the same request ID after an uncertain mutation and read authoritative status before reporting completion. Binding and security-transition retries reauthorize before returning their existing result. Cancellation withdraws a pending approval request; it does not undo a completed human decision. A browser cancel, OAuth token error or missing grant does not fabricate a success or deliberate-revocation receipt.

The secondary CLI remains for automation, diagnostics and protected recovery. It does not authenticate a human merely because an agent invoked a command. Keep human secrets outside chat, tool arguments and worker-readable environments; do not expose internal owner operations through generic dispatch wrappers.

Tests exercise exported domain handlers plus installed Auth session lookup and MCP token/grant handlers over serialized synthetic databases. These validate implementation boundaries under the fixture's stated assumptions. They do not prove Convex transaction contention, deployed component wiring, actual JWT verification, host delivery, browser credentials or live revocation races. Component declarations are reconciled offline against the pinned published `ComponentApi` types; deployment/code generation is a separate controlled step.
