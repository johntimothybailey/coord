# Linux cgroup containment

`createCgroupControl` in `src/containment.ts` is the built-in Linux cgroup-v2 control. It requires the operator-selected `root`, the same `metadataRoot` used by `LaunchJournalStore`, an exact `CapabilityKey`, current capability evidence and `checkCurrentConfiguration()`. It returns `preflight()`, `prepare(launchId)`, `attach(receipt)`, `adapter` and `close()`. It adds no service, broker or dependency. The direct daemon passes `containment: control` and `stopAdapter: control.adapter` to `createLaunchSupervisor`.

Run `preflight()` before reserving capacity. Its read-only checks require actual Linux, cgroup2 filesystem magic, a canonical delegated non-root directory, valid domain type and controller files, a single visible cgroup2 mount with mount root `/`, a matching cgroup namespace, and a supervisor already within that delegated subtree but outside launch groups. Permission checks open the relevant control files without writing. They do not mount filesystems, change controllers, migrate a process or create a probe group. The first implementation rejects ambiguous mounts, namespace-relative mount roots, threaded groups, escaped paths and unsupported host platforms. This Mac reports unsupported before controller/credential access.

The recomputed configuration digest must include the exact cgroup root, journal root and native permission policy identifiers. Standard managed qualification plus one additional current real check, `process.cgroup-control-isolation`, is mandatory. That evidence must demonstrate worker denial of controller writes, migrations/escape, `/proc/<supervisor-or-wrapper>/fd` and `/proc/<pid>/root` aliases, and supervisor journal modification under the actual harness/OS policy. A writable delegate root, mode 0600 or an agent's statement does not establish isolation. Provider/human credential isolation remains independently required. No real Linux setup is qualified by these tests.

`prepare` runs after the launch journal exists. It first fsyncs a private create-only intent in `<metadataRoot>/<launchId>/cgroup-binding.json`, then creates only `<root>/coord-<launchId>`. An existing intent or group is a reconciliation hold; it is never borrowed, emptied or reused. The group must be empty and valid. Prepared metadata binds boot, namespace, mount/membership path, directory device/inode and capability-key digest. Metadata lives outside cgroupfs, which does not support arbitrary application files. No automatic group removal or ancestor kill is implemented.

The wrapper receives only a strongly typed cgroup specification. Before recording its process receipt or starting a harness, it opens the exact prepared group and writes kernel PID zero to `cgroup.procs`, which selects the writing process rather than racing a parent-supplied PID. It verifies its resulting membership and adds the local containment binding to its receipt. The wrapper retains its own kill descriptor for independent watchdog cleanup; it is not intentionally passed through harness stdio. Actual native policy must also deny the worker descriptor aliases. The parent never moves a live PID: `attach` confirms the retained IPC/durable receipt, exact journal/run identity, native boot/start identity before and after membership reads, and kernel membership. It fsyncs an attached record before backend authorization. The supervisor repeats this confirmation before release.

The parent retains an open group directory. Control paths through its own descriptor bind operations to that kernel object, and named-path device/inode checks reject replacement. A stop request writes only `1` to that owned group's `cgroup.kill`, then waits with bounded I/O and polling. Recursive `cgroup.events` reporting `populated 0` supplies positive tree-exit evidence only after exact attachment was established. Empty direct `cgroup.procs`, wrapper exit, missing PIDs and successful signals are insufficient. Stop evidence is fsynced outside cgroupfs and remains bound to the original receipt. Observing a changed actual kernel boot ID can instead establish verified reboot. Missing/replaced groups, malformed/inaccessible state, timeout and receipt/configuration mismatch retain the hold.

Restart reads both the protected attached record and exact original launch journal receipt. It cannot accept a caller's `attached` claim or recover from missing prepared state. Reopening a group requires its original path/device/inode; deployment policy must prevent deletion/reuse by workers or unrelated coordinators. A released journal cannot trigger another kill. `close()` closes this instance's retained handles and removes no group or durable state. Backend outcome acceptance and exactly-once reservation release remain separate supervisor operations.

Execution admission and physical cleanup use separate authority paths. The active controller remembers an exact owned receipt only after fresh owner/configuration qualification and confirmed native attachment. Its stop/observe operations need no backend query or renewed execution permission. They still verify the protected attached record/journal and current local kernel boot, namespace and exact group identity. A backend outage, revoked execution grant or expired admission proof cannot by itself prevent killing that already owned containment. It also cannot make a missing group, root exit or empty PID search into positive proof.

Restart cleanup constructs `createCgroupControl({...originalControl,lifecycleOnly:true,verifyLifecycleOwnership})`. The mandatory trusted callback validates the original protected route/runtime/machine/member/key/check provenance locally for the exact receipt and returns its original key; it must not depend on a backend call. Cleanup-only controllers reject preflight, prepare and attach unconditionally. Historical ownership authorizes only stopping/observing that original attached tree, never a new launch or renewed execution. Positive evidence is fsynced locally before any backend handshake or confirmation. When the backend is unavailable, local exit evidence and the held reservation remain for later authenticated, idempotent confirmation.

The kernel documents inherited membership, recursive populated state, delegation boundaries and whole-subtree kill in its [cgroup-v2 guide](https://docs.kernel.org/admin-guide/cgroup-v2.html). Kernel PID-zero behavior is explicit in the [cgroup implementation](https://github.com/torvalds/linux/blob/master/kernel/cgroup/cgroup.c). The adapter uses these kernel facts only within a selected configuration whose no-escape policy was independently demonstrated.

Tests explicitly label positive scenarios as syscall fixtures: they substitute kernel control-file behavior and never move or kill a real process. They cover self-only attachment, exact receipt/journal binding, nested live descendants despite empty direct PID lists, group/PID replacement, collisions, absent isolation proof, bounded unknown state and restart/reboot reconciliation. The real current-host test proves unsupported Mac behavior. A delegated Linux VM, native cgroup access-denial tests, actual model runs and the two-machine pilot remain unverified requirements.
