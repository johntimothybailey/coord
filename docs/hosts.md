# Host interfaces and qualification

Adapter arguments were checked against Codex CLI 0.146.x, Antigravity `agy` 1.4.x and Claude Code 2.1.x on macOS arm64. Re-verify versions on your own host; a version check is not a qualification. Adapters construct argument arrays for these actual CLIs and request sandboxing. They do not establish permission isolation or managed eligibility.

| Host | Installation interface (not executed) | MCP interface | Check-in definition |
| --- | --- | --- | --- |
| Codex | `codex plugin marketplace add PATH`; `codex plugin add coord@MARKETPLACE` | `codex mcp add coord -- coord mcp` | `hooks/hooks.json`: SessionStart and PreToolUse |
| Antigravity | `agy plugin install ./plugins/antigravity` | `agy mcp add coord coord mcp` | `hooks.json`: SessionStart, PreInvocation and PreToolUse |
| Claude Code | `claude plugin marketplace add PATH`; `claude plugin install coord@MARKETPLACE` | `.mcp.json`: `coord mcp` | `hooks/hooks.json`: SessionStart and PreToolUse |

Build the package and make its `coord` bin available on PATH before using either plugin. Its MCP entry is `coord mcp` (`node dist/src/cli.js mcp` from this checkout). Hooks use `coord hook HOST EVENT`, receiving event JSON on stdin. No credentials belong in plugin files. The Codex package uses its supported compatibility manifest; Antigravity uses its native manifest and `mcp_config.json`.

Codex plugin hooks require explicit host trust. Native hooks are guardrails with coverage limits, and Antigravity hook errors fail open. Cooperative MCP check-ins remain required when hooks are unavailable. A package manifest, validator result or returned JSON does not prove registration, turn injection, or acknowledgement. Only a tested host session may produce that evidence; actual delivery, backend registration, credential isolation, and two-machine acceptance remain BLOCKED until exercised.

Safe discovery commands run here: both hosts' `--version` and `--help`; `codex plugin --help`, `codex plugin add --help`, `codex plugin marketplace add --help`, `codex mcp add --help`, `codex exec --help`; `agy plugin --help`, `agy mcp add --help`. Antigravity documents `agy plugin validate PATH --strict --json`; `agy plugin validate --help` is rejected by version 1.4.2, so use `agy plugin --help` for that syntax. No model turn or host installation was executed.

The maintainer's redacted capability ledger separates host-command support from actual Coord discovery and delivery. `agy plugin validate ./plugins/antigravity --strict --json` passed with one skill, one MCP server, one hook group and no findings. The stdio MCP tests use the real SDK transport with a fixture backend; they do not qualify a real host or deployed backend.

## Conversational workflows and human confirmation

Every Coord workflow is intended to start in the host conversation through a plugin/skill and typed tools. The CLI is a supporting interface for automation, diagnosis and terminal fallback. This applies to setup, status, goals, tasks, learning, approvals, pause/resume, checkpoints, review, membership and backend operations. Each conversational action must retain the same backend permissions, exact-revision checks and recovery behavior as its underlying operation. Current plugin support is partial: rule/lesson review and expiring rule approval-request tools/skill are implemented, with passkey-backed human completion through the protected HTTPS page. Actual host delivery and physical authenticator qualification require separate evidence.

The host-support check separates four kinds of evidence: vendor documentation, installed interfaces, an actually negotiated/displayed interaction, and qualification of the protected human decision plus credential isolation. These are not interchangeable.

| Host | Documented conversation/confirmation interface | Installed interface evidence | Actual dialog and protected approval |
| --- | --- | --- | --- |
| Codex | Plugins/MCP support conversational tools. App-server documents MCP form and URL elicitation, with accept/decline/cancel responses. | The inspected CLI generates an app-server schema containing MCP elicitation form/URL request shapes and response actions. | Native protocol responses: **OBSERVED** Accept/Cancel with the nonce form and Decline with the fieldless Deny form; display and choices are user-reported. Headless automatic decline is separate. Rule completion uses an enrolled passkey in the protected HTTPS page; native prompt acceptance still grants no authority. Physical device/host qualification remains separate. |
| Claude Code | Skills and MCP support conversational tools. Documentation describes form and URL dialogs; advertised modes depend on version and connection. Elicitation hooks can answer without displaying a dialog. | Version/help confirms skill, plugin, MCP and permission-control interfaces. It does not prove the installed client's elicitation modes or UI behavior. | Dialog/negotiated client capabilities: **UNKNOWN**, not exercised. Sources: [Codex app-server elicitation](https://learn.chatgpt.com/docs/app-server), [Codex MCP](https://learn.chatgpt.com/docs/extend/mcp), [Claude MCP elicitation and version-dependent capability declarations](https://code.claude.com/docs/en/mcp#respond-to-mcp-elicitation-requests), [Claude elicitation hooks](https://code.claude.com/docs/en/hooks#elicitation), [Antigravity MCP and tool permissions](https://antigravity.google/docs/mcp), [Antigravity headless permissions](https://antigravity.google/docs/cli/headless/).

A form's `accept` result, a tool permission prompt, a skill instruction or a model's statement that the user agreed is not sufficient protected-human evidence. Claude hooks may supply responses programmatically; Codex's separate user-input interface also has an automatic-resolution option. Never collect vault passphrases or approval credentials in chat/form results. The passkey approval adapter authenticates the human action outside model control and binds it to the displayed project, record, revision and content hash. Cancellation, stale content, unavailable host features or ambiguous actor identity must leave approval unrecorded; an uncertain backend reply requires readback rather than a claimed rollback.

**Read-only review implementation:** `coord_review_memories` and `coord_review_memory`, routed by the existing skill, list proposed rules/active lessons and expand exact source data without requiring a participating run. See [coverage, connection and recovery details](commands.md#conversational-review). The tools never grant human authority; existing MCP sessions need to reconnect after upgrading to discover them. Their fixture coverage does not qualify actual host delivery. For actual rule approval, use the passkey-backed browser link described in the [command workflow](commands.md#conversational-rule-approval-requests). URL elicitation is a convenience; a safe clickable link works when that mode is unavailable. Neither native callback is authenticated approval.

The bounded checks used only version/help, installed protocol definitions and official documentation. A repeatable Codex interface inspection is `codex app-server generate-json-schema --out <temporary-directory>`; inspect the generated MCP elicitation request/response types. It generates protocol files, not a user approval. No model turn, host configuration change, plugin installation or real approval was part of this check. Exact observed versions and raw local artifacts belong in the maintainer's local evidence, not this generic matrix. Recheck after host upgrades. Missing evidence is **UNKNOWN** or **BLOCKED**, not a claim that a host cannot support the workflow.

### Approval request handoff

The existing skills route “approve this proposed rule” to exact source review and `coord_request_rule_approval`, then present a pending request with server expiry. `coord_approval_request` reads current state and `coord_cancel_approval_request` withdraws only that request. This uses project authority before task registration; the request cannot grant human authority, complete from a host form or access an approver credential. See [the envelope, retry and authorization boundary](commands.md#conversational-rule-approval-requests). The protected passkey view completes the request independently of native confirmation callbacks; backend status is the authoritative outcome.

### Synthetic confirmation probe

The package provides `coord_confirmation_probe` for “test confirmation” requests and an isolated MCP mode, `coord mcp --confirmation-probe`, requiring no project or backend credentials. It asks only about a fresh synthetic no-effect record. Use a temporary host MCP configuration and record the allowlisted negotiated capability/response observations; see [probe behavior and evidence limits](commands.md#no-effect-host-confirmation-check). Do not treat generated protocol schemas, programmatic accept/decline/cancel handlers or a `prepared` observation as evidence that native UI appeared.

Codex distinguishes text-entry forms from fieldless action choices. The [version-pinned TUI source](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/tui/src/bottom_pane/mcp_server_elicitation.rs#L1170-L1234) submits populated fields as Accept; [Esc dispatches Cancel](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/tui/src/bottom_pane/mcp_server_elicitation.rs#L1527-L1538). A fieldless, non-tool-approval form exposes **Deny** as a distinct Decline choice. The dedicated `coord_confirmation_decline_probe` / `coord mcp --confirmation-decline-probe` requests that shape without changing the nonce form. The source mapping was checked with one native `declined_response` after the user reported selecting the visible Deny option. This establishes an observed protocol path, not authenticated human authority. Typed `decline` in a nonce field is not that control.

A host with no declared form capability returns an explicit unverified observation. An accepted matching nonce remains a host response with no human identity or approval authority. Real dialog display, user interaction and automatic-answer behavior must be observed separately before choosing a protected adapter. The capability matrix above remains conservative until such evidence exists; testing this probe does not qualify credential isolation or real approval.

## Claude Code support boundary

Claude Code is supported for **advisory** participation only. Its plugin uses the documented standard layout: the manifest at `.claude-plugin/plugin.json`, `.mcp.json` and `hooks/hooks.json` at the plugin root, and `skills/coord/SKILL.md`. `claude plugin validate ./plugins/claude` passes with no warnings. Its `PreToolUse` hook consumes `tool_name` and returns the same `hookSpecificOutput` envelope Codex uses, with `permissionDecision` and `permissionDecisionReason`; `SessionStart` injects `additionalContext` and cannot block.

Managed launch and read-only replanning are **explicitly unsupported** for this harness, and `selectedAdapter` cannot reach a Claude adapter because `claude` is deliberately absent from the runtime harness enum in `src/command-runtime.ts`. Two separate reasons, neither resolved by configuration:

- Claude Code's `--permission-mode` and allowed-tool lists are a different enforcement model from the `--sandbox workspace-write` / `--sandbox read-only` contract the Codex paths rely on. A flag rename is not a proof.
- No protected runtime startup binding has been demonstrated. The plugin registers plain advisory `coord mcp`, which by design cannot mint a manual registration or renew a run.

The backend also constrains `capabilityKey.harness` to `codex` or `antigravity` in `convex/schema.ts`, so no Claude capability key, qualified machine record or manual registration can be submitted at all. Widening that union is a schema change requiring a deployment, and it is **not** done. Until it is, `coord_register_manual` rejects `harness: "claude"` before any backend request, which is the intended fail-closed behavior rather than an oversight.

The `PreToolUse` matcher is `Bash|Edit|Write|NotebookEdit` rather than `.*`. A denial is only ever possible on a mutation tool, so matching read tools would add a subprocess and a backend round trip per read with no enforcement benefit. The deliberate consequence is that check-in context and message receipts are delivered less often than on a `.*` matcher, so T5 delivery evidence for this harness must be read against the narrower matcher and not assumed equivalent. Writes performed through `Bash` are observed, but Coord still cannot see a mutation that a tool outside this list performs.


## Protected runtime actions

Trusted startup can run `coord mcp --runtime <protected-file> --session <admitted-session>` to connect the worker's stdio tools directly to the bounded command graph. No separate IPC service is required. Startup resolves protected routing and credential locations and binds one exact run, epoch, goal revision and launch ID. Every callback revalidates that binding. The model's tool arguments cannot choose a runtime file, session, credential, shell command or attestation.

| Tool | Accepted arguments | Meaning |
| --- | --- | --- |
| `coord_checkpoint` | `checkpointId` | Request audited capture/publication through the fixed runtime. |
| `coord_review` | `checkpointId`, `publicationId` | Request or reconcile exact review publication, with backend authority checked on each attempt. |
| `coord_finalize` | `outcome`: `succeeded`, `failed` or `stopped` | Request finalization; a stale local renewal error does not bypass or prevent backend authorization. |
| `coord_finish_replan` | `result`, up to 20 dependency proposals, bounded `rationale` | Return a revised, blocked or failed result from the admitted replanning run. |
| `coord_dependency_input` | `dependencyTaskId` | Read compact metadata for the current task's exact declared dependency pin; never choose an arbitrary task or full manifest. |

The callbacks are absent in an ordinary advisory MCP connection; runtime tool calls then return an explicit configuration blocker. They expose no approval, raw backend, merge, deployment or verifier route. Successful review, finalization or replanning closes ordinary writes and local renewal. Finalization and exact review reconciliation still reach the protected helper, which decides current authority. A source-data receipt never grants permission for more work and does not prove process exit or capacity release.

Trusted startup may return a cleanup-only binding after independently validating the accepted review state. Such a restarted server begins with ordinary writes, registration, replanning and renewal closed; only protected review reconciliation and finalization callbacks remain available. A persisted receipt alone cannot choose this mode or recreate execution authority. Dependency lookup fixes the current task from its bound run and requests metadata without the private manifest. Availability and exact refs/commits/trees identify source material; they do not imply merge, automatic integration or substitution of a newer artifact.

Codex startup supplies fixed nonsecret MCP command arguments for the protected runtime/session. Qualification still requires current owner-provisioned `mcp.runtime-actions` evidence and all other applicable checks. Antigravity runtime mode remains unsupported unless its actual configured plugin path and fixed startup binding are independently proven. SDK callback fixtures and the disposable parsed-command graph exercise implementation behavior; neither is real host qualification. No paid model execution or global plugin installation is part of those tests.

Sources: [OpenAI plugin packaging](https://developers.openai.com/plugins/build/plugins), [Codex hooks](https://learn.chatgpt.com/docs/hooks), [Antigravity plugin format](https://antigravity.google/docs/build-plugins), [Antigravity hooks](https://antigravity.google/docs/hooks/), [Antigravity headless mode](https://antigravity.google/docs/cli/headless/). Consult these alongside the installed CLI help before changing arguments or manifests.

Plain `coord mcp` is advisory read/propose only; it cannot mint a manual registration or renew an execution by accepting model-supplied host qualification. Participating sessions enter through qualified resume/daemon startup and use the protected runtime bridge. Host identity and evidence are derived and revalidated by that trusted path, never asserted by tool arguments.

## Passkey-backed human rule approval

The chat tool opens a first-party HTTPS view on the project's paired `.convex.site` origin, with no private rule data before passkey authentication. One-time operator enrollment binds a browser-created public key to an existing human-role credential after exact fingerprint comparison outside the agent. Routine approval needs only the browser/passkey interaction and backend status recovery, not command entry. Review and decision assertions are distinct; only an atomic backend decision can report approval. No human token or private signing key is given to the plugin.

Hosts with URL elicitation can present the page natively; other hosts present the trusted link. This does not depend on managed/manual task admission or a model-authored confirmation. Browser WebAuthn support, required user verification, fixed origin/RP binding and an unrevoked human enrollment are required. Software authenticators used in tests demonstrate signature/permission logic, not physical-device attestation or full host isolation. [W3C assertion verification](https://www.w3.org/TR/webauthn-3/#sctn-verifying-assertion) and [browser public-key access](https://developer.mozilla.org/en-US/docs/Web/API/AuthenticatorAttestationResponse/getPublicKey) describe the underlying platform interfaces.

The protected human browser/profile and review UI must remain outside worker automation control, alongside operator code and backend deployment authority. Passkey protocol checks do not qualify isolation from a worker that can alter that surface or deploy different authorization code.
